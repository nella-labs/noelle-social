# LinkedIn Growth Intern ("Lyra") — operator guide

Lyra is Noelle's second first-class agent: a **draft-only** LinkedIn sibling of the X intern (Vega). She has **two discovery lanes** (parallel to Vega): a **watch lane** — re-reading the operator's LinkedIn connections and replying to their posts — and a **search lane** — keyword-searching LinkedIn-wide for high-engagement posts from people *outside* the network that match the objective. She profiles authors and drafts a reply for each, queued for human approval. **It never posts to LinkedIn and never auto-sends.** (Auto-DMs are opt-in, **off by default** — `dm_autodraft_enabled`, 0036.) She can also draft **one warm intro DM per watched connection, ever** (relationship-building, no pitch) — also opt-in, **off by default**, toggled per-agent from the Config page (`linkedin_intro_dm_enabled`, 0039); see [Intro DM lane](#intro-dm-lane-one-time-relationship-building).

This guide describes the LinkedIn worker. See [the runtime runbook](runbook.md) for managed operation.

> **Actuation is separate.** Auto-liking, auto-commenting, and auto-DMing are handled by the **LinkedIn Actuator** Chrome extension — documented in `docs/linkedin-actuator.md`. Lyra herself remains draft-only; the actuator only consumes what Lyra's pipeline has already approved.

## Architecture (parallel to the X intern)

| Piece | Path |
|---|---|
| Voyager client (read-only) | `packages/linkedin-client` |
| Worker app | `apps/linkedin-intern` — workers: `discovery` → `classifier` → `drafter` (+ `profiler`, + `ideation` & `post-drafter` for the Posts lane) |
| Agent type | `packages/agents` (`registry/linkedin_intern.yaml`, `types/linkedin_intern.ts`, `chat/linkedin_intern.ts`) |
| Schema | `infra/cloudsql/schema/0027`–`0029` (`linkedin_watchlist_people`, `linkedin_watchlist_profiles`, seed); `0037` (`linkedin_watchlist` keyword topics — the search lane); `0038` (`linkedin_watchlist_people.intro_dm_drafted_at` — the intro-DM "once, ever" stamp) |
| pm2 | configured by `apps/cli` (`linkedinWorker()` in `process-manager.ts`) |

Reuses the platform-agnostic pipeline: `noelle.leads` (`platform='linkedin'`) → `noelle.drafts` (`kind` `reply`/`dm`) → `noelle.approvals`, plus `@noelle/runtime` (Codex routing, budget, voice KB, tenancy).

**No `send` worker exists** — Lyra never posts; drafts only ever queue for human approval (there is no auto-send path anywhere). Both lanes insert each post as a **new, unclassified** lead (`status='new'`, `priority=false`); the **classifier** then grades every lead against the objective (it no longer "replies to everything"), and the drafter claims the ones that clear the bar. The bar — the q-score threshold (0–100, post drafted when `q >= threshold`) — defaults to `LINKEDIN_Q_THRESHOLD` (75) but is **operator-settable per-instance** on the **Config page → Classifier filter** (`agent_instances.classifier_threshold`, migration `0042`; the worker resolves `inst.classifier_threshold ?? env`). Lower it (≈50–60) to loosen the filter when the approval queue is thin.

**Priority clamp (watchlist-only, off-topic floor).** A hand-picked **watch-lane** connection (a person the operator chose to follow — the watch lane leaves `payload.source` unset) is never hard-skipped on a borderline post: the classifier's `skip` is clamped up to a short `light` note ("the person is the gate, not the post"). Two guards keep this from drifting off-topic (`apps/linkedin-intern/src/workers/classifier-tick.ts`): (1) the clamp applies **only** to genuine watchlist connections — the algorithmic lanes (`source='profile_search'` Feeder A ICP guesses, `source='keyword'` search) are **not** rescued, so a guessed author's off-topic or hiring post honours the classifier's `skip`; (2) even a watched connection's post is only rescued when its `q` clears the off-topic floor `CLAMP_MIN_Q` (default 25, env `NOELLE_LI_CLAMP_MIN_Q`) — so a genuine milestone (q≈35) still gets a warm note while an off-topic/hiring repost (q≈5–20) stays a skip. Substantial/light verdicts always pass through unchanged. (Before this, every `priority=true` lead — including profile-search guesses — was clamped, so Lyra replied to off-lane posts like an education-sector advisory-board announcement and "we're hiring" reposts.)

**English-only gate (always on).** Before the LLM triage, the classifier runs a deterministic English detector (`apps/linkedin-intern/src/lib/language.ts`); a post judged non-English is dropped to `skipped` (`reply_kind='skip'`, `payload.classifier.skip_reason="non-english"`) with no LLM call — so a French/Spanish/German/Portuguese post never gets a non-English draft. The detector is lenient (short/emoji/link-only/ambiguous text and any post with a real English function word pass through as English). Mirrors the X intern's gate; see `docs/classifier-grading.md` step 0.5.

### Two discovery lanes (watch + search)

Lyra's discovery mirrors Vega's two-lane model (`apps/linkedin-intern/src/workers/discovery.ts`):

- **Watch lane** (`linkedin_watchlist_people`, the dashboard **Watchlist** toggle) — the LinkedIn connections she watches. Always-on while `watchlist_enabled`: it keeps replying to your network even after a goal reaches/stalls + auto-pauses, and **bypasses** the goal + backpressure caps. It still shares the daily **extract** cap (`LINKEDIN_DAILY_EXTRACT_CAP`, a cost/backlog safety limit) — but the top band of that cap is **reserved** for it (`LINKEDIN_WATCHLIST_DAILY_RESERVE`), so the search lanes can never spend the whole budget and leave the watch lane starved. For each watched person, discovery fetches their recent posts via Apify `profilePosts`. Manage on the **Watchlist** page: add a connection by LinkedIn URL / `/in/<slug>` / bare slug, set a free-text per-person objective, or remove someone. People are keyed by `public_id`.
- **Search lane** (`linkedin_watchlist` keyword topics, the dashboard **Discovery** toggle — labelled "finds new posts to reply to") — free-text topics Lyra searches LinkedIn-wide via the Apify **post-search** actor (`buIWk2uOUzTmcLsuB`) for high-engagement posts from people *outside* the network. Active-only and **gated** by the goal + inbox/backlog backpressure (so it stops adding strangers once the queue is full or the goal is hit). The actor can't sort by engagement or exclude authors, so the worker over-fetches by recency and filters client-side: skips **company** pages (`author.type`), drops posts below the **reaction floor**, drops posts outside the **time window**. Search posts carry their own (stranger) author, so the lead's `author_handle` is the post author's public id (`publicIdentifier` falling back to `universalName`) and `author_id` is null. Edit the keyword list on the **Watchlist** page under **Keywords · search lane**. Empty keywords = search lane off (watch-only). Knobs: `LINKEDIN_KEYWORD_DISCOVERY_LIMIT` (posts/keyword), `LINKEDIN_KEYWORD_MIN_REACTIONS` (default floor when `discovery_config` sets none), `LINKEDIN_KEYWORD_POSTED_LIMIT` (actor recency hint).

The **Pipeline panel's "Tailor this run"** applies to Lyra. Apify attaches each post's posted-at + reaction/comment counts, so both lanes honour: **posts from the last N hours**, **posts per connection** (`LINKEDIN_DISCOVERY_LIMIT`), and **min reactions / min comments** floors. `minReactions` doubles as the **search lane's high-engagement floor** (a configured value wins over the env default). These persist as `agent_instances.run_config` (per-run override) over `discovery_config` (saved default) and resolve in `apps/linkedin-intern/src/lib/discovery-config.ts` (`resolveLinkedinDiscovery`); the X-only search-operator fields (min likes/replies, exclude retweets/replies, lang) don't apply.

**Inbox: "Per person → Latest only" filter.** A chatty connection can stack several drafts in the approvals inbox at once. The `Per person` filter (URL `?wlLatest=on`) collapses the list to **one post per connection — the newest** (by the post's `posted_at`, falling back to the approval's created-at). It's opt-in (off by default) and shared with Vega's inbox; every Lyra lead is a watched connection, so it collapses the whole list. It applies to **Review, Speedrun, AND the detail-page "draft N of M" stepper** — the stepper parses the LinkedIn filters off the link (`parseLinkedInApprovalFilters`, which now includes `wlLatest`) and walks the same collapsed/filtered queue, so prev/next + auto-advance never drift from the list. Implemented as `keepLatestLinkedInPostPerPerson` over the already-per-post-deduped views (`apps/app/src/lib/queries.ts`).

**Inbox: Skip controls + Configure (Vega parity, minus posting).** The Lyra approvals surface mirrors Vega's *minus every send/auto-send affordance* (she's draft-only):

- **Skip in Speedrun** — every speedrun card (both interns) now has a one-click **Skip** beside Mark sent. It flips the lead's pending reply angles to `skipped` via `/api/drafts/:id/skip` (the route skips siblings server-side, DMs preserved); the card clears optimistically and the progress bar counts it as cleared. Shared `SpeedrunRow`/`SpeedrunInbox`.
- **Review-inbox Skip/Unskip + bulk Skip** — `LinkedInReviewInbox` is now a client component with the X inbox's per-row ✕ (skip) / ↩ (unskip) and a multi-select **"Skip selected"** bar. **No "Auto-send selected"** — Lyra has no send worker. Reversible under **Status → Skipped**.
- **Detail-page Skip** — `LinkedInReviewPanel` gained a panel-level **Skip** (only when there's a reply to skip) that skips the lead and auto-advances, like its **Mark sent**.
- **Configure agent →** — `LinkedInStream` now carries the same config deep-link Vega's `XInternStream` does (`agentHref(orgSlug, lyra, "config")`).

Note: auto-DMs are **off by default** (`dm_autodraft_enabled`, 0036) — Lyra drafts replies only. Flip them on per-instance under **Configure agent → Direct messages** (same toggle exists for Vega). The bulk-DM inbox affordances stay hidden while DMs are off.

### Multi-lane: Replies · DMs · Posts (+ always-on Intelligence box)

Lyra is a **multi-lane agent**. One shared **Intelligence box** — Watchlist + Profiler + the new **Engagement Analyst** — runs regardless of lane pause and feeds three independently-triggerable lanes:

- **Replies** — the discovery → classifier → drafter funnel above (reply comments).
- **DMs** — the companion DM (rides a high-value reply) + the proactive intro-DM lane below.
- **Posts** — a brand-new, two-stage, generate-on-demand content pipeline (below). Never auto-publishes.

Lane on/off lives on the agent page's **Lanes** card. Replies → `drafter_enabled`, DMs → `dm_autodraft_enabled` (+ `linkedin_intro_dm_enabled` for intro DMs), Posts → `agent_instances.lane_config.posts.enabled` (migration `0049`). The `ideation` + `post-drafter` workers gate on the Posts lane flag.

**Who the profiler profiles.** Two lanes feed its work queue (merged by `lib/profiler-queue.ts`, watchlist first, capped at `PROFILER_BATCH`):

1. **Watchlist people** (`linkedin_watchlist_people`) whose profile is missing or older than `PROFILE_REFRESH_DAYS` — the accounts the operator selected. Hand-curated; `source` is `manual` for every row today.
2. **People we actually talk to** — anyone with strictly more than `PROFILER_MIN_REPLIES` (default **5**) **SENT** replies within the last `PROFILER_REPLY_WINDOW_DAYS` (default **90**), via `listRepliedPeopleNeedingProfile`. The search/keyword lane meets people the watchlist never hears about, and before this they were never profiled at all: every reply to them was drafted with no idea who they were. Reply count is the durable "this is a real relationship" signal.

   The recency window matters: a lifetime tally would be **monotonic**, so nobody could ever leave lane 2. Removing a person from the watchlist would then stop no spend at all — the profiler would keep re-fetching them every `PROFILE_REFRESH_DAYS` forever. The window keeps the signal meaning "someone we are *actively* talking to" and bounds the queue by the reply rate rather than by all of history.

Lane 2 deliberately does **not** auto-promote into `linkedin_watchlist_people` the way Vega does on X (`x-intern/src/lib/watchlist-promote.ts`). Watchlist membership also grants always-reply priority and makes the person eligible for a proactive **intro DM** (`intro_dm_drafted_at IS NULL`), so promoting on reply count would fire outbound DMs as a side effect of wanting a profile. Widening the read-only queue gets the grounding with no blast radius.

**Key mismatch (the trap).** Three distinct id spellings collide here, and all three bit:

- Profiles are keyed by `fsd_profile_id`, but a lead's `author_handle` is whatever the discovery lane captured — sometimes the vanity slug, sometimes the member urn. The query matches an existing profile under **either** key and carries that row's `fsd_profile_id` forward, so a re-profile UPDATEs the row instead of inserting a twin.
- The Apify actor sometimes returns the opaque member urn (`ACwAA…`) as `publicIdentifier`. `profilePosts` is keyed on `linkedin.com/in/<slug>`, so those people backed off forever with *"no public_id"*. `resolveVanitySlug` (in `@noelle/linkedin-apify`) mines the real slug out of the person's own `linkedin.com/posts/<slug>_…` permalink, both at normalize time and when queuing. `isMemberUrnId` is deliberately **case-insensitive with a 30-char floor**: these ids reach us lowercased through some paths, while a real slug like `achim-bonsch-a9186a38` (21 chars, starts with `ac`) must not be mistaken for one.
- The drafter's profile lookup key is `lead.author_id`, but the **keyword lane inserts leads with `author_id = null`** and the ICP lane's fsd id is often absent in the actor's short mode. `getWatchlistProfiles` therefore aliases every profile under its lowercased vanity slug too, and the drafter falls back to that key — otherwise a profile written for such a person is paid for and then silently never read.

**Engagement Analyst** (a second pass inside the `profiler` worker, `lib/engagement-analyst.ts`) ranks watchlist authors by the real engagement already on their posts (`leads.payload.reactions/comments`) and distills the top performers into reusable **playbooks** (`noelle.watchlist_playbooks`, migration `0048`): hook patterns, structure, cadence, top topics. Feeds Posts ideation and the post-drafter. Tunables: `LINKEDIN_ANALYST_TOP_AUTHORS`/`_BATCH`/`_WINDOW_DAYS`/`_MIN_POSTS`/`_SAMPLE_POSTS`.

### Posts lane (two-stage, generate-on-demand)

The operator's "give me post ideas + draft them" pipeline. **Stage 1 — ideation** (`ideation` worker, on operator request via `noelle.ideation_requests`, migration `0050`): gathers four sources — watchlist engagement mining, net-new keyword search (Apify post-search `buIWk2uOUzTmcLsuB`), vault voice/pillars, and the Analyst playbooks — and proposes **idea cards** (`noelle.post_ideas`, migration `0045`) with a hook, thesis, and the posts they're "inspired by" (clickable refs). No full draft is written yet.

**Stage 2 — generate on demand:** the operator reviews ideas in **Approvals → Posts → Ideas**, clicks **Generate** (idea → `approved`), and the `post-drafter` worker claims it, gathers context (vault voice + the inspiration posts' text + playbook hooks + pinned drafter rules + any per-post chat guidance), writes the full post (Opus-tier `post-drafter` bucket), runs the **verifier** (the same em-dash + slop hard-zero judge as replies, `NOELLE_POST_VERIFY` defaults on), and writes a **post draft** (`noelle.post_drafts`, migration `0046`). Review in **Approvals → Posts → Drafts** (edit inline, **Mark ready**, **Copy out**, Dismiss) — Lyra never posts, so ready posts are pasted to LinkedIn by hand. **Weekly batch** mode lays 7 ideas across a Mon–Sun calendar (**Posts → Week**).

**Drafter chat** (`Refine` on a post): tell the drafter a frame, a personal anecdote, or what to avoid → the post regenerates with your guidance (it re-queues the idea so the worker re-gathers; the new draft supersedes the old). Tick **Save as a standing rule** to pin it (`noelle.drafter_notes`, migration `0047`) so it applies to every future post. Pillars come from `NOELLE_POSTS_PILLARS` (CSV); verify retries from `NOELLE_POST_VERIFY_RETRIES`.

### Intro DM lane (one-time, relationship-building)

Separate from both the reply lane and the post-reply DM above: Lyra can draft **one warm intro DM per watched connection, ever**. Its only purpose is to start a relationship beyond replying to posts — a genuine peer note that references the person's work and **asks what they're currently building**. **No pitch** (no product, link, or CTA — it's relationship-building, not outreach). It's queued for approval as a synthetic, **post-less** DM (`kind='dm'`); like everything Lyra does, it's **draft-only and never auto-sent**.

- **Default OFF, per-instance dashboard toggle.** `agent_instances.linkedin_intro_dm_enabled` (migration `0039`, default false) — a normal switch on the agent's **Config page → Direct messages → "Intro DMs"** (LinkedIn only). The worker resolves `inst.linkedin_intro_dm_enabled ?? LINKEDIN_INTRO_DM_ENABLED` (the env var is now only a legacy fallback for a worker that booted before the column existed). It only runs while the instance is **active** (the watchlist reply lane still runs while paused; the intro-DM backfill does not).
- **Never during a goal-run.** A goal-run ("get N **replies** ready") is a replies-only objective, so the intro-DM lane is hard-gated off whenever `goalTarget(inst) != null` — even with the flag on. Otherwise intro DMs (post-less leads) bury the inbox and the run pauses before N real replies exist. Intro DMs trickle only on normal (non-goal) ticks.
- **Personalized only.** A person is eligible only when they have a **generated profile** (`linkedin_watchlist_profiles.summary IS NOT NULL`) — an unprofiled connection waits for the profiler. The DM is grounded in the person's summary/topics/tone/engagement-notes (+ per-person objective).
- **Exactly once, paced.** `claimIntroDmPeople` (in `apps/linkedin-intern/src/lib/watchlist-db.ts`) atomically **claims + stamps** `linkedin_watchlist_people.intro_dm_drafted_at = now()` under `FOR UPDATE SKIP LOCKED` (mirrors `claimDmRequestLeads`), so each person gets one intro DM and never re-drafts. `LINKEDIN_INTRO_DM_DAILY_CAP` (default 5, `0` disables) paces the one-time backfill across days. A crash after the claim but before posting loses that single DM (acceptable — the flag is already stamped), same trade as the per-person watchlist claim.
- **Voice.** Reuses the same NEVER-DO rules as the reply prompt (no em-dashes, no corporate verbs, no "as a fellow…", English-only) plus a hard no-pitch rule; `SYSTEM_LINKEDIN_INTRO` + `renderIntroDmPrompt` in `prompts.ts`, drafted by `runIntroDmTick` in `workers/drafter-tick.ts`. Aim 300–550 chars (700 hard max), fragmented into 3–5 `\n` chunks. `stripEmDashes` + `stripDisallowedEmoji` are the hard backstops and `char_count` is recomputed off the cleaned body.

**Approval UI note (post-less DM).** The intro DM has no source post, so the synthetic lead carries `originalPostId='<fsd_profile_id>:intro'`, `originalPostText='(intro DM — relationship outreach, not a reply to a post)'`, `originalPostUrl='https://www.linkedin.com/in/<publicId|fsd>/'` (the person's profile, not a feed-update link), and `postKind='intro_dm'`. The approval detail will render that placeholder string where the "original post" normally shows, and the "open original" link points at the person's profile rather than a post — expected, not a bug.

**Replies are the unit; DMs are an extension.** Across the app a "draft from Lyra" / "lead ready" means a **reply to a post**, never a standalone DM. So: the goal count + stall clock (`goal.ts`), the pending badge (`countPendingLinkedInApprovals`), and the "N drafts from Lyra" headline all count **distinct reply leads only** (`drafts.payload.kind='reply'`) — a reply with an attached DM counts once; a post-less intro DM counts zero. The Review + Speedrun inboxes **hide standalone DM cards by default** behind a `DMs: on/off` toggle (the shared `useShowDms` hook, same as the X intern); reply-with-attached-DM rows already collapse to the reply card upstream, so only standalone DMs get hidden.

### Draft-DM button + progressive DM ladder (on-demand)

A **"Draft DM" button on each post** in the Lyra approvals inbox (the Speedrun card's action strip and the review **detail** panel, LinkedIn posts only). Clicking it flags the lead behind that post for a DM (`payload.dm_requested`, via the `requestDmForLead` server action, org-scoped, tenancy-checked); Lyra's drafter claims it next tick (`claimDmRequestLeads`) and queues a DM for approval. Draft-only — never auto-sent. Same `dm_requested` mechanism as the Contacts **Generate DM** button, so both entry points go through one drafter path.

The DM it drafts is **not a cold pitch**. It's the *next rung* of a four-step relationship ladder toward a call, chosen by **how many DMs the operator has already SENT that person** (`countSentDmsToAuthor`, `lib/dm-ladder-db.ts`):

| Sent | Rung | What the DM does | Proposes a call? |
|---|---|---|---|
| 0 | **Open** | React to one specific thing in their post + one genuine question. | No |
| 1 | **Deepen** | Another genuine touch; share a bit of your own experience. | No |
| 2 | **Bridge** | Name the real overlap; float "worth comparing notes sometime." | No (soft) |
| 3+ | **Invite** | Propose a low-pressure quick call (~15 min), easy to decline. | Yes |

Model: `lib/dm-ladder.ts` (`DM_RUNGS` + `pickRung`) is the pure ladder; `buildLadderDmSystem(rung)` + `renderLadderDmPrompt(...)` in `prompts.ts` render a rung, grounded in the post + person + the bodies of prior DMs sent to them (`getRecentDmsToAuthor`, so the next rung doesn't repeat an earlier opener). `runDmRequestTick` (drafter-tick) wires it. The call ask is gated by `rung.proposesCall`, so rungs 1–3 hard-forbid it and only Invite may suggest talking live — "start small, then progress; the objective is a call, but never on the first touch." Same anti-slop voice as the intro DM (no em-dashes, no buzzwords, no pitch; `stripEmDashes` + `stripDisallowedEmoji` backstops). Rung advances only when the operator actually **sends** the prior DM (progression follows real sends), so drafting several rung-1 DMs across a person's posts before sending is harmless (all gentle, no premature call). The rung is logged; a per-draft visible badge + the review-inbox-list button (the tight 40px action column) are follow-ups.

## Connection (the important part)

Lyra talks to LinkedIn's **Voyager API** over HTTPS GET. Two facts make it work (see memory `reference_linkedin_voyager_connection`):

1. **Residential IP.** Run it on the **Lima `default` VM** (egresses the configured host network via NAT). A GCP datacenter IP gets 302'd and **permanently burns the cookie** — never run Lyra on `noelle-vm-0`.
2. **Mint a fresh JSESSIONID.** The DevTools/pasted JSESSIONID is stale (`403 "CSRF check failed"`). The client GETs an authenticated page with `li_at`, takes the JSESSIONID LinkedIn sets, and uses it as the csrf-token. So **`li_at` is the only credential**.

**li_at is disposable + IP-pinned:** using one `li_at` from more than one egress IP gets it invalidated (`Set-Cookie: li_at=delete me`). Capture it from a browser and run Lyra from **one** residential egress (the VM). When it dies, drop a fresh `li_at` in and `pm2 restart` discovery+profiler.

## Credentials

Self-host stores `li_at` VM-local only, never GCP Secret Manager, never the repo:

```
# ~/.noelle/.env  (mode 0600, inside the Lima VM)

```

The worker resolves it via `secrets.get("linkedin-li-at")` (env on self-host; GCP SM `linkedin-li-at` on a managed box).

## Cadence (how it stays unbanned)

Tuned via env (`apps/linkedin-intern/src/env.ts`), conservative defaults:

| Env | Default | Meaning |
|---|---|---|
| `LINKEDIN_MIN_DELAY_MS` / `LINKEDIN_JITTER_MS` | 20000 / 70000 | 20–90s jittered window between Voyager calls |
| `LINKEDIN_MAX_CALLS_PER_HOUR` | 90 | rolling-hour ceiling (client throws → tick defers) |
| `LINKEDIN_ACTIVE_HOURS_START/END` + `LINKEDIN_TZ_OFFSET_MIN` | 7 / 23 / -300 | only touch LinkedIn 7am–11pm Bogota |
| `DISCOVERY_POLL_MS` / `PROFILER_POLL_MS` | 15 min | not a tight loop |
| `LINKEDIN_DISCOVERY_LIMIT` / `LINKEDIN_PROFILER_LIMIT` | 5 / 40 | gentle (watch-lane) discovery; deep read for profiling |
| `LINKEDIN_KEYWORD_DISCOVERY_LIMIT` | 15 | posts fetched per keyword (search lane); Apify bills per result |
| `LINKEDIN_KEYWORD_MIN_REACTIONS` | 10 | search-lane reaction floor when `discovery_config` sets none |
| `LINKEDIN_KEYWORD_POSTED_LIMIT` | week | coarse recency hint to the post-search actor |
| `LINKEDIN_DAILY_EXTRACT_CAP` | 0 (unlimited) | per-instance ceiling on leads discovery EXTRACTS per calendar day, summed across **all** lanes (watch + keyword + profile). A cost/backlog safety cap — applies even to the always-on watch lane. `0` = no cap; volume is then governed by the goal auto-pause + backlog backpressure + the rate limits above. The day boundary is the DB's `current_date`, i.e. **America/Bogota**, not UTC. |
| `LINKEDIN_DAILY_SUBSTANTIAL_CAP` / `LINKEDIN_DAILY_LIGHT_CAP` | 0 / 0 (unlimited) | per-instance ceiling on how many SUBSTANTIAL / LIGHT posts the **drafter** drafts per calendar day (independent buckets). `0` = no cap. **Do not re-impose these to protect the account** — drafting is draft-only, it fills the approval queue and never touches LinkedIn; the write-side valves are auto-send pacing and `LINKEDIN_MAX_CALLS_PER_HOUR`. A fixed daily bucket starves the queue instead: the 24/7 drafter drains the whole day's quota against the overnight backlog within ~an hour of the midnight reset, so every scheduled/manual run afterwards defers all its leads back to `classified` and reports `0 / N leads ready` with no visible reason. |
| `LINKEDIN_WATCHLIST_DAILY_RESERVE` | 40 | of `LINKEDIN_DAILY_EXTRACT_CAP`, how many extractions/day are **reserved for the watch lane**. The keyword + profile SEARCH lanes stop feeding once the day's total reaches (cap − reserve), so a burst of low-value search/profile leads can't starve the operator's own connections. `0` = no reserve (old shared, first-come pool). |
| `LINKEDIN_WATCHLIST_REPOLL_HOURS` | 4 | watch-lane **per-person re-poll cooldown**: a watched person's `profilePosts` is fetched at most once per window. The extract cap counts new **leads**, not actor calls, so without this every person was re-fetched every 15-min tick (~96×/day/person — mostly zero-result runs that still burn Apify credit and aren't even metered to `llm_calls`). 4h ⇒ ≤6 sweeps/day/person (~94% fewer watch-lane calls). In-memory per process (a restart = one extra full sweep); `0` disables. |

One LinkedIn session per process (one mint, reused across ticks). The Voyager **client** reads JSON only and never fetches media. Post **image URLs**, however, do come through the Apify post actors (`postImages`, video thumbnail, article image, carousel pages) and are captured on the lead payload as `images[]` for the drafter's vision-caption step — see `docs/grounded-drafting.md`.

## Drafting voice + comment-energy

The drafter (`apps/linkedin-intern/src/lib/prompts.ts`, `workers/drafter-tick.ts`) writes a tighter, more human comment than a raw LLM would:

- **Pick one thread.** It develops the single most reply-worthy thing in the post instead of summarising the whole thing (covering everything is the #1 bot tell). A short, specific personal closer ("hope Lisbon was worth it") is welcome.
- **Length.** Comments are 1–2 sentences, aim ~90–180 chars with a ~220 hard ceiling (was ~200–350, originally ~600). The prompt leads with "ONE sharp sentence" rather than a fill-the-range target, because an explicit upper bound makes the model anchor high. DMs — **off by default**; only drafted when `dm_autodraft_enabled` is on, and then only for T1 — stay 400–700.
- **Emoji allowlist.** A draft may use an emoji **only when the source post itself uses emoji**, and only from `💀 😭 😛`. Enforced two ways: the prompt asks, and `stripDisallowedEmoji` (`@noelle/runtime`) hard-strips anything else from every shipped body and recomputes `char_count`. Same rule applies to Vega on X.
- **Comment-energy.** Before drafting, the drafter fetches the **existing comments** on the post (Apify `harvestapi~linkedin-post-comments`, via `@noelle/linkedin-apify` `postComments`) and injects a reaction-ranked digest + the total count into the prompt, with the instruction to match the room and **not repeat a take already made** — the more comments a post has, the harder it differentiates. Gated on a known comment count ≥ `2`, capped at `LINKEDIN_DRAFTER_COMMENT_MAX` (40), and fail-open (an Apify error just drafts without comment context). Off when no Apify token is configured.
- **Per-person memory (don't repeat yourself).** Before drafting, the drafter pulls the reply bodies it already **sent or queued to this same person** (`getRecentRepliesToAuthor` in `lib/prior-replies-db.ts`, matched by `author_handle`/`author_id`, `edited_body` preferred, sent ranked first) and injects a "do NOT repeat these takes/openers" block. Without it, when a connection posts several times Lyra re-said the same thing every time. Tuned by `LINKEDIN_DRAFTER_SENT_TOPK` (default 3, `0` disables); fail-open; replies only (DMs untouched).
- **Post images (vision).** When a lead's payload carries `images[]` (both discovery lanes capture them now), the drafter captions them and injects "THE POST'S IMAGE SHOWS: …" so the text-only model can react to the chart/screenshot/meme. The caption fn prefers a BYO org `gemini-api-key`; with none (the self-host case) it falls back to **Vertex Gemini via the worker's ADC service account** (`createVertexCaptionFn`, gated on `NOELLE_VERTEX_ENABLED`, default on) — so captions work with **no extra key**. Fail-open everywhere: no images / no Vertex / a vision error all degrade to text-only drafting.

- **Anti-AI sweep (the `anti-ai` skill, READER mode).** Lyra carries the reader-facing tell list from the operator's `anti-ai` skill, enforced on both legs. Proactively, `ANTI_AI_RULES` in `prompts.ts` is injected into all five prose surfaces (`SYSTEM_LINKEDIN`, `SYSTEM_LINKEDIN_BASE`, `SYSTEM_LINKEDIN_LIGHT`, the intro DM, the ladder DM). Deterministically, `scoreFormat` in `@noelle/runtime` hard-zeroes three new families when its `strictVoice` flag is on (`ctx.platform === 'linkedin'`):
  - **Significance markers** — sentences whose only job is to say what another sentence *meant* ("that's the part that got me", "here's the thing", "and that's the point", "let that sink in"). The skill's cleanest evidence: a text passing every other check scored 100% AI, and deleting exactly two of these flipped it to 100% Human. The fix is **deletion, not rewording**, and the verifier reason says so.
  - **Reader-mode constructions** — copula dodge (`serves as`/`represents`), participial tails (`…, underscoring its role`), vague authority (`studies show`), false suspense (`here's the kicker`), grandiosity (`pivotal moment`). Shape-level tells a regex can't judge in a 100-char comment (rule of three, invented concept labels, burstiness) stay prompt-only.
  - **Tier-1 wordbank** — `delve`, `leverage`, `tapestry`, `seamless`, `myriad`, `furthermore`, `it's important to note`, and ~50 more. Words with a valid technical meaning (`robust`, `ecosystem`, `trajectory`, `navigate`, `harness`) are deliberately **excluded** from the deterministic list and left as prompt guidance, so "a robust parser" survives; a test pins that exclusion so re-adding them is a conscious decision.

  **Calibration.** Every rule was swept against the live corpus before landing (`noelle.drafts`, n=1646 replies/DMs; `noelle.post_drafts`, n=43 LinkedIn posts). Newly hard-zeroed: **1/1646 replies (0.06%)** and **1/43 posts (2.3%)**, both true positives per the skill's explicit lists. Getting there killed a first draft of the rules that false-positived on real operator voice — `leverage` as the founder-sense noun ("know your leverage", in a *published* post), `serving as` on role/promotion posts (the exact content Lyra comments on), `functions as` in code talk, `underscore` the character, `elevated` p99 latency, owned data ("our benchmark data shows"), and proper nouns (`Endeavor`, `Profound Documents`). Each is pinned by a must-pass test. **Words with everyday or technical senses stay prompt-only** — `robust`, `ecosystem`, `trajectory`, `navigate`, `harness`, `realm`, `beacon`, `endeavor`, `profound`, `relentless`, `tireless`, `represents`.

  **Scope:** LinkedIn only today, which also covers Lyra's **post** lane (`post-drafter-tick.ts` verifies with `platform:"linkedin"`). Posts are ~6.5x longer than replies, so they absorb a proportionally higher hit rate — re-sweep `noelle.post_drafts`, not just `noelle.drafts`, before widening any rule. Flipping this on for Vega/Orion is a one-line change at the `scoreFormat` call site.
  **The `honestly` tic has a soft penalty.** One natural use can clear the format bar; repeated use or another pattern penalty lowers the score enough to regenerate. The shared scoring owner and tests define the thresholds.

  **What a hard zero actually does.** It does *not* block a draft. `runVerifyLoop` retries up to `NOELLE_DRAFTER_VERIFY_RETRIES` (default 2), then queues the best candidate anyway with `pass:false`; the only skip path is the separate voice floor, which reads the judge's `voice` score, not `format`. So the cost of a false positive is extra regenerate calls plus a fix prompt that tells the drafter to delete its best line — a quality regression, not queue starvation. The corollary is that these rules *nudge* rather than enforce: ~3.5% of already-sent replies still contain a pre-existing hard-zero phrase.

  **Not adopted:** the skill's DETECTOR mode (discourse fracture / interleave protocol). Those recipes target 120–160 **word** first-person rants and need invented names, prices and dialogue as scaffolding — incompatible with a ~100-char reply and with Lyra's no-fabrication HARD BAN, which she has no swap-in step to satisfy. The post-drafter carries the same tell list plus a burstiness rule, since a post is the only Lyra surface long enough for a statistical detector to score at all.

**Classifier score is 0–1.** `noelle.leads.classifier_score` stores the LLM `q/100` (the shared approval UI multiplies by 100). Storing the raw 0–100 `q` is the "7800/100" bug — fixed in `classifier-tick.ts`; migration `0032` backfilled existing rows.

## Style sources (Account Feeder)

Lyra learns a human writing **form** from admired accounts. On a manual, paid Run (Styles page) the feeder pulls each source's recent posts + authored comments (`account_style_posts`), distils each into a Gemini "ultra profile" (`account_ultra_profiles`: voice/tone/structure/hooks/signature phrasings/topics), and the drafter samples high-performing exemplars per lead and injects their FORM. The account-feeder owner defines the extraction and selection contract.

- **Extraction needs a real timeout.** The distillation sends ~60 posts to Gemini; the key backend's 8s default aborted it every run (`"gemini call: This operation was aborted"` → 0 profiles). The feeder now passes `STYLE_EXTRACTOR_TIMEOUT_MS` (90s) via `selectGeminiBackend`. Vertex ADC separately dies with `invalid_rapt` on the residential VM — `NOELLE_GEMINI_API_KEY` (a BYO AI-Studio key) is the working path.
- **Selection.** `NOELLE_DRAFTER_STYLE` (on) gates per-lead exemplar selection (`lib/style-select.ts`): Voyage `rerank-2.5` for fit × engagement percentile × register-aware cheer, with controlled variety. `NOELLE_DRAFTER_DENSE` adds the **dense/vector** layer — pgvector `voyage-3-large` embeddings RRF-fused with the rerank. The feeder embeds corpus rows (`voyageEmbed`, backfill + newly-pulled) into `account_style_posts.embedding`; without embeddings the hybrid ranker fails open to rerank-only.
- **Posts, not comments (`styleExemplarKinds`).** Each source is stored as original posts (`kind='post'`) and authored comments (`kind='comment'`). The reply drafter defaults to **posts only** — a person's original posts are their considered, high-signal voice; their comments are often sloppy throwaways that dragged replies down (this was the "it's shaping my replies from their comments" complaint). `account_feeder_config.styleExemplarKinds` (default `['post']`, read by `readStyleExemplarKinds` in `@noelle/runtime`) selects the kinds; the drafter loads **every** requested kind and concatenates them into the one pool `selectStyleExemplars` ranks by fit + engagement. Set `['post','comment']` to fold comments back in (the older "pool both" behaviour), or `['comment']` for comments-only. Toggle it in-product on the **Styles page → "Shape replies from"** (Posts only · Posts + their comments), or via the `setStyleExemplarKinds` server action — applies on the drafter's next tick, **no restart** (the drafter reads the config per tick). Both the blend and the pin path honour it. **Follow-up:** the ultra profile is still distilled from both kinds; restricting distillation to posts-only when a source's comments are especially noisy is a later refinement (kicks in on the next paid feeder Run).
- **Pin one exact voice.** The Selection above *blends* the whole enabled pool. To write in **one named person's** exact style instead, set `account_feeder_config.pinnedStyleHandle` to a source's canonical handle. The **Style picker** on the post detail page (`content/[ideaId]`) sets it; so does typing **"follow Kaia's style"** in the drafter chat — the posts-chat route (`api-vm` `POST /api/posts/:ideaId/chat`) runs `extractStyleDirective` + `resolveStyleSourceHandle` (`@noelle/runtime`) to map the name → handle and pin it (with an agent confirmation note). When pinned, **both** the post drafter (`kind='post'`) and the reply drafter (kinds per `styleExemplarKinds`, **posts-only by default**) load ONLY that account's corpus + ultra profile via `listStyleExemplarsForHandle` / `getUltraProfileForHandle`, **enabled-independent** (a pin overrides the source's `enabled` flag), style forced **on** even when the `NOELLE_*_STYLE` env gate is off, and the exemplar count floored at `PIN_MIN_EXEMPLARS` with variety 0 (`pinnedSelectConfig`). Only the FORM is pinned — the operator's own Mars voice still grounds the CONTENT. Clear it (picker → "Automatic") to return to the blend. **NB:** this also activated the post-lane style seam, which the `post-drafter` worker never actually loaded before (F8 was dead in prod).
- **Form-variant rotation (every reply, not just pinned ones).** Each reply is assigned ONE of **12 FORM VARIANTS** (`@noelle/runtime` `formVariants.ts`: micro 3-8 words · one short sentence · hook-then-line · question-only · observe+ask · two flat sentences · long run-on · parenthetical-aside · fullest 2-3 beat ~320 chars · detail zoom · **self-story** · **agree-and-extend**) picked by weighted random choice **excluding the previous pick's variant**, so the rotation never picks the same shape twice in a row (process-wide state, survives across ticks; a lead that errors/defers between two picks can, rarely, leave two same-shape replies adjacent). The last two are LinkedIn-only: Lyra and Vega used to run the SAME ten skeletons in two length bands, which is a large part of why the two feeds read as one writer (Vega's exclusives are `RIFF` and `FLAT_DISAGREE`). **The shape fires on every lead.** It used to be gated on a pinned faithful voice, because the directive was rendered INSIDE the faithful STYLE block — so an unpinned lead got no shape at all and fell back to the fixed "~90-180 chars, ~220 ceiling" line at the bottom of the user prompt. Measured over 30 days that pinned her feed at **181 ± 44 chars** while Vega's, which has had a standalone block since #498, spread **131 ± 58**. Now: a pinned lead still renders the shape inline (replacing the faithful block's own hook-then-line recipe), and every other lead gets the standalone `THIS REPLY'S ASSIGNED SHAPE` block (`renderAssignedShapeBlock`) — including the batched-light lane, which previously had no form directive at all. **The closing length line is now shape-aware**: it is the LAST line the model reads, so a fixed char band there silently outranked any shape above it. **Tone-first lane:** on a CELEBRATION post with no pinned voice the energy-aware REGISTER wins instead (mirroring tone beats varying form on a win), mirroring Vega. Shape and register are never both present — both claim reply length. The **light lane excludes QUESTION_ONLY** (a bare question can't carry a congrats) and `FLAT_DISAGREE`. Browser-observed replies also exclude `QUESTION_ONLY`, `SELF_STORY`, `AGREE_EXTEND`, and `MICRO`; the bare-question shape repeatedly asked for metrics absent from the post. Comments only, never the DM. With `NOELLE_DRAFTER_VARIETY` off, nothing is injected and the fixed band is restored.
- **Attribution.** Each draft records the voice blend it learned from (`buildStyleSource` → `payload.style_source`, e.g. `{blend:[{handle,weight}]}`); the approval card + inbox show a `Style: kaia-tham 67% · annielongg 33%` pill (`StyleSourceBadge`), layered on the operator base voice (Mars).
- **Observability.** The Styles page shows, per source: pulled post/comment counts, last-pull time, a styled/not-styled badge, and an expand with the actual top pulled posts + the Gemini interpretation. A contact who is also a style source gets a "Style source" card (with the ultra-profile) + list badge on Contacts; `reconcileContactsForOrg` materializes every source as a contact.
- **Brand applies to every intern.** `noelle brand apply` (and the auto-apply on `noelle up`) now writes `brand_config` to all drafting roles (`x_intern`, `linkedin_intern`, `reddit_intern`) — previously Vega-only, which left Lyra on the hardcoded fallback prompt.

## Cost / billing (Apify is metered)

Every Apify actor run is recorded to `noelle.llm_calls` with `engine='apify'` (tokens 0). The cost is **Apify's real per-run figure** — the client reads `usageTotalUsd` off the finished run (it starts the run async via `POST /v2/acts/{id}/runs`, polls to a terminal state, then fetches the dataset items) and passes it to `apifySpendRow({ actualUsd })` in `@noelle/runtime`; the rotating client forwards it to the token that actually paid. `estimateApifyCents` (the old hardcoded ~$2/1k table) survives **only as a fallback** when a run reports no usage. Recorded for profile-posts in **discovery** + **profiler**, and the **drafter**'s comment fetch. It is **excluded from the budget cap** — both the enforcement (`packages/runtime/src/pgBudgetAdapters.ts`, called with `CAP_EXEMPT_ENGINES_APIFY`) and the Budget panel (`getInstanceSpendThisMonth`) filter it out, so the LinkedIn data fetch never starves the LLM budget. It still shows on the dashboard **Spend** page, which splits **AI vs Apify** (`getOrgSpendBySourceMonth`), and per-token on the Connections card. Bound per-lead comment cost with `LINKEDIN_DRAFTER_COMMENT_MAX` (0 disables comment-energy).

**Apify tokens are a hot-swappable fallback _pool_ + per-token spend is tracked.** Add one or more tokens on the dashboard **Connections** page ("Data sources" → Apify) — stacking several is encouraged, because the free Apify tier caps at **$5/mo** and the discovery cadence burns it fast. They're stored in `noelle.connections` (DB-backed, not Secret Manager), so the workers read the active pool each tick via `createApifyResolver` with **no restart** (env `NOELLE_SECRET_APIFY_TOKEN` is used only when the pool is empty). Each run stamps `llm_calls.credential_id` with the token that paid, so the card shows spend **per token** and the old token's history survives a removal.

**In-use vs spare buckets (migration `0058`).** Tokens carry an `in_use` flag splitting the pool in two: **in use** (`in_use = true`) is the live rotation the agents pull from; **spare** (`in_use = false`) is a parked holding bucket no worker ever touches. The Connections card has a **bulk paste box** — drop in many tokens at once (one-per-line / comma / space separated; `parseApifyTokens` trims, de-dupes, drops fragments `< 12` chars) and they all land as **spare**. Promote the ones you want with **Move to in use** (and demote with **Move to spare**); both flip `in_use` via `setApifyConnectionInUse` without disturbing spend history or exhausted/invalid state. `listApifyTokens` filters `in_use = true`, so a spare token is invisible to the resolver — and the same shared pool feeds Lyra, Orion, and Vega (all three `listApifyTokens` queries gained the filter). If **no** token is in use the resolver falls back to the env token, exactly as when the pool is empty.

**Fallback + exhaustion (migrations `0040`/`0041`).** The resolver returns a *rotating* client (`apify-rotating.ts`): each call tries the **available** tokens in order and when one returns a token-fatal error it rotates to the next, transparently and mid-tick, recording *why* by HTTP status: a **403 "Monthly usage hard limit exceeded"** benches the token until its **real billing-cycle reset** — probed live from `/v2/users/me/limits` → `monthlyUsageCycle.endAt` (+1h buffer), so it re-enters rotation the moment Apify refills the $5 instead of a flat +30d guess; only when the probe can't report a cycle (or on a **402** payment error) does it fall back to `DEFAULT_RETRY_COOLDOWN_DAYS` (~30d). A **401 "token not valid"** is **verified before retiring** (`checkApifyToken`): a single transient 401 (a throttle during a burst) used to permanently kill a perfectly good token, so now the token is health-checked first — only a probe that *also* 401s sets `invalid_at` (genuinely wrong / deleted / **banned**); an alive/inconclusive probe gets a short 1-day cooldown instead. An invalid token is **excluded from the pool the instant it's flagged** (`listApifyTokens` filters `invalid_at is null`, so it leaves every worker's candidate set *and* the pool count immediately — repeated 401s from a banned account on one IP are an abuse signal that endangers the rest of the pool) and rendered **"invalid · replace"** in the UI, until the operator re-pastes a good one. A token is **available** again once `retry_at <= now()`, so it re-enters rotation on its own billing date even while other tokens still work — it then either succeeds (its `exhausted_at`/`retry_at` clear) or re-cools for another window. Still-cooling tokens are *skipped*, not retried, so no 403 calls are wasted; the resolver passes the full pool size so the error is accurate. When **every** token is spent (or all cooling) the discovery worker records `worker_runs.error` (the Pipeline panel shows the Discovery row as **errored: all N Apify tokens exhausted…** instead of a silent "stalled") and fires a **Pushover** ping (`pushover-user-key` / `pushover-token`, once per episode — re-armed when a token works again). Transient 429 rate-limits are *not* token-fatal: they bubble and defer to the next tick. The Connections card shows each token's status + its **retries `<date>`** when cooling.

**Goal stall-guard.** A goal-run ("get N **replies** ready") auto-pauses not only when it reaches N but also when it makes **zero progress for `LINKEDIN_GOAL_STALL_MIN`** (default 2h) — so a target larger than the watchlist can produce (e.g. 20 from 17 quiet people) can't poll Apify forever. The pause log says `stalled` vs `reached`. Both the progress count and the stall clock count **reply leads only** (`drafts.payload.kind='reply'`), so a trickle of intro DMs can neither "reach" the target nor reset the stall clock.

## Connection follow-up (on-demand)

A one-shot operator tool for the moment you **just connected** with someone and want to build a *genuine* relationship, not pitch them. You name the person; Lyra scrapes their recent posts + the comments they've authored on other people's posts (the same read-only Apify actors the profiler uses — no `li_at`, no session risk), reuses any profile she already wrote for them, and generates a **connection brief**:

- **Common ground** — real shared ground / why they're worth knowing, grounded in their actual work.
- **Talking points** — specific, concrete things from their posts/comments worth referencing.
- **Genuine questions** — a list of curious, specific questions a real peer would ask (the point of the tool).
- **A follow-up DM** — one warm, first-person note, no pitch/product/link, in the same anti-slop voice as the intro DM (no em-dashes, no "Curious:", no buzzwords; `stripEmDashes` + `stripDisallowedEmoji` are the hard backstops, and one plainer regeneration fires if the DM still trips a phrase tell).

It's **draft-only** like everything Lyra does: it prints to the terminal, you copy the DM and send it by hand. Nothing is queued or auto-sent, and it never touches LinkedIn directly (Apify only).

Run it on the Lima VM (the residential egress). Two equivalent ways:

```bash
# via the noelle CLI (loads ~/.noelle/.env for you)
noelle lyra followup https://www.linkedin.com/in/kaia-tham
noelle lyra followup kaia-tham --posts 25 --json

# or the native worker gesture (the one-shot loads ~/.noelle/.env itself)
cd apps/linkedin-intern && ./run.sh followup --person /in/kaia-tham
```

The person accepts a full profile URL, an `/in/<slug>` path, or a bare slug (normalised by `linkedinPublicId`, the same helper the Watchlist add uses). Flags: `--posts N` (default 20, max 50), `--comments N` (default 12, max 40; `0` skips authored comments), `--json` for machine-readable output. Code: `apps/linkedin-intern/src/workers/followup.ts` (one-shot entrypoint) + `src/lib/followup.ts` (prompt, schema, anti-slop scrub — unit-tested).

**Model + cost.** The brief rides **Opus** (`opusOverrideRouting(linkedinInternRouting(inst))`): `claude -p` first when the claude-cli backend is selected, Bedrock Opus otherwise, falling back to the instance's normal model (Sonnet) only if Opus is unavailable — the same high-quality path as the VIP/intro DM, and just one LLM call per run so cost is negligible. The Apify `profilePosts` + `profile-comments` fetches are metered to `noelle.llm_calls` (`engine='apify'`, `worker='followup'`) exactly like the profiler, so they appear on the **Spend** page's Apify column and never draw down the LLM budget cap.

**Prereqs.** Needs the worker built (`noelle up --workers`, or `pnpm --filter @noelle/linkedin-intern build`), an Apify token (dashboard → Connections → Data sources), and a `linkedin_intern` instance (created by `noelle migrate`). If the person posts rarely and has authored no comments, there's nothing to ground on and the command says so instead of inventing a brief.

## Operate (Lima VM)

1. Put a fresh `li_at` in `~/.noelle/.env` (see above).
2. Apply migrations: `noelle migrate` (the `0027`–`0029` files are picked up by the ledger). Confirm: `select role,status from noelle.agent_instances where role='linkedin_intern';` → `Lyra`.
3. Seed the watchlist on the agent's **Watchlist** page: add each connection by LinkedIn URL / `/in/<slug>` / bare slug (with an optional per-person objective), or bulk-seed via the connection import. Optionally pre-set a saved discovery default (window + engagement floors) under Configure agent → Discovery; per-run overrides come from the Pipeline panel's "Tailor this run".
4. Start workers: they're in the generated `ecosystem.config.cjs` as `noelle-linkedin-{discovery,profiler,drafter}`. `pm2 start ecosystem.config.cjs` (or `pm2 restart` after an env change).
5. Drafts land in the approvals inbox → copy → send on LinkedIn by hand → **Mark sent**.

If `li_at` dies: discovery/profiler log a `LinkedInAuthError`; drop a fresh token and `pm2 restart noelle-linkedin-discovery noelle-linkedin-profiler`.
