# X actuator build plan (Phase 4)

## Daily reply cap

The actor panel's daily reply cap is the hard ceiling for browser reply admission. X can optionally vary the effective cap each database calendar day between a saved minimum and that ceiling. Enabling variation starts today's cap at the ceiling. Later days choose another integer in the range and persist it, so reloads and concurrent requests keep the same value. Saving the same range preserves today's value; tightening the range clamps it without exceeding the new ceiling. A fixed-cap save disables variation.

The panel shows today's effective cap separately from the editable ceiling and minimum. Queue serving, final target reservation, the remaining counter and instance health use the same policy in `apps/api-vm/src/lib/x-browser-reply-cap-db.ts`. Usage remains organization-wide and includes unresolved reservations. The cap limits admission; it does not promise that many published replies. This setting does not change the official API budget, reply review, STOP, send consent or other platforms.

## Discover + Reply hours (current behavior)

The in-page **Discover + reply automatically** button runs around the clock by default. Its optional **Pause replies and likes during quiet hours** switch saves a local-time window; the initial times are 01:00–09:00. The start is included and the end is excluded, including across midnight. Browsing continues during the window, while replies, likes, and any DM action wait for a later paced slot.

The extension restores this setting after restart and reads it again before each write. A change does not interrupt a reply already being sent. The saved discovery window takes precedence over the legacy Auto curfew while Discover + Reply is active; Manual Auto and Auto retain their own behavior. Existing send caps, stop and challenge controls, deduplication, and review checks still apply.

The floating panel now uses the same shared layout as LinkedIn: active reply leads against the five-slot discovery limit (for example, `2/5`), run state, and errors. Discover and Stop are the visible actions; quiet hours and legacy modes sit in collapsed sections. The old on-page activity console is gone. The count comes from the server's discovery-capacity endpoint once per minute; if unavailable, it falls back to the actor's loaded ready replies and shows an error.

The X reply actuator is the twin of the LinkedIn actuator (`apps/linkedin-actuator`). X replies must go through the browser because the official API is dead for automated replies (see `docs/reply-actuation-strategy.md`), and bird is retired. This is the execution-ready spec.

**Honest status:** everything here is a mechanical mirror of the LinkedIn actuator EXCEPT the X DOM locators, which must be built and tuned against a live, logged-in `x.com` session (they cannot be verified headless). That one piece is why this ships as a plan, not merged code, in this branch. All the hard parts (the CDP input engine, the human-motion model, the scheduler, pacing, autonomy, warm-up, the detection hardening) are already built and shared.

## Reply failure handling (ported from the LinkedIn actuator, PR #437)

A reply attempt now returns a staged result instead of a bare boolean, and the queue can no longer be starved by one bad tweet:

- **Verified submit.** After clicking the reply submit, the background confirms via `readCommentBox` that the composer cleared (or tore down) — only a confirmed clear returns ok. The old path returned true straight after the click, so a missed/rejected submit was marked sent with nothing posted. `not-cleared` (a submit was clicked but the composer never cleared — a wall of these across tweets is the signature of a live reply action-block) vs `submit-not-found` (no clickable submit ever appeared — selector drift) name the failure. This is now subsumed by the `background/submit.ts` pipeline (`runSubmitReply` + `replyFailureDecision`, see § Send integrity below): a reply that actually landed is never re-queued, so no duplicate replies.
- **Reason grammar.** A failed attempt logs `reply-failed:<detail>` (or `reply-failed:gave-up-after-N:<detail>`) in `noelle.x_activity.reason` — `box-not-found` / `submit-not-found` / `not-cleared` name the failing stage without a live DevTools session. (Only the `ambiguous-dropped` skip rows carry a `tweet_id`: the server dedup counts a tweet_id-stamped skip as reply evidence, so it must never be stamped onto retryable failures — see § Send integrity below.)
- **Retry cap + back-of-queue.** A failed draft is re-queued at the BACK of the pool with a per-session `tries` counter; at `MAX_ACTION_TRIES` (3) it is dropped for the session (`doneDraftIds`), so one broken tweet can't monopolize the lane ("wall of reply-failed" starvation). `tries` survives replenish (mergePool keeps existing items).
- **Dead tweets are skipped durably — with a structurally gated detector.** `detectPostUnavailable` trusts `[data-testid='error-detail']` (X's dedicated error container) unconditionally, and trusts the interstitial phrase probe ("This post was deleted by the post author." / "These posts are protected." / "Hmm...this page doesn't exist.") ONLY when no `article[data-testid='tweet']` exists on the page — the same phrases render inside embedded quote cards of deleted tweets and in ordinary reply prose on perfectly healthy permalinks, and a false positive here fires a DURABLE server write. On a hit the draft is dropped locally AND marked skipped server-side via the shared `POST /api/actuator/mark-skipped/:id` (status='pending' guard — it can never clobber a sent/errored approval), so the queue stops re-serving the dead permalink on every future run. A false negative merely costs a capped retry.

## Drain auto-continue (ported from the LinkedIn actuator, PR #439)

A drain plans a FIXED number of reply slots (the queue size at Drain time), so it used to stop after that first batch even when the inbox still held approvals (mid-run arrivals, retry re-queues). Now, when every planned slot is done and the run is `mode:"drain"`, `maybeExtendDrain` re-fetches the queue (filtered against `doneDraftIds`, so retry-capped drafts stay dropped) and — per the pure `shouldExtendDrain` predicate — appends a fresh batch of comment+like slots, extends the window, and bumps `RunState.drainRounds`. One operator Drain clears the WHOLE inbox. **Persistent (never re-click):** an empty served queue no longer ends the drain — per `drainShouldKeepWaiting` the run stays `running` and re-checks the queue every ~75 s (`DRAIN_WATCH_POLL_MS`), rolling its window forward, so a reply approved later goes out with no re-click. Only **STOP**, a **challenge halt**, or the runaway ceiling `MAX_DRAIN_ROUNDS` (raised 50 → **1000**, counting actual send-batches only) end it; forever-failing drafts still hit the per-draft retry cap. The appended batches reuse `drainShortBandProb`, X's short-band pacing knob.

`XActivityEventSchema`'s per-event fields (`approval_id` / `tweet_id` / `author_handle` / `reason`) are `.nullish()` (not `.optional()`), mirroring the LinkedIn activity batch-500 fix: an explicit JSON `null` in one event must not make the whole up-to-200-event batch throw and silently drop every row the dedup/caps read back.

## Drain gap patterns (no fixed reply → likes → reply shape)

Every drain gap used to look identical: reply, 4–8 likes evenly scattered, next reply. A rigid shape repeated all session is itself a fingerprint, so each between-reply gap now draws a **behavior pattern** from the plan RNG (`GAP_PATTERNS` in `apps/x-actuator/src/lib/scheduler.ts`):

| Pattern | Weight | Shape of the gap |
|---|---|---|
| `full` | 34% | likes scattered through the whole gap — the legacy shape |
| `cooldown` | 26% | **zero likes** AND a genuine quiet pause — the gap is drawn from the NORMAL band (60–120s) even under `shortBandProb`, so it reads reply → step away → reply |
| `light` | 18% | just 1–3 likes |
| `frontload` | 11% | likes bunched into the first ~40% of the gap, then quiet |
| `backload` | 11% | quiet first, likes only in the last ~40% |

There is deliberately **no `cluster` pattern on X** (Lyra keeps a small one, trimmed to a 1–2-like pair): rapid like bursts are exactly the machine-cadence velocity signal X locks on (`docs/x-account-safety.md` §4), so cooldown is weighted up. (Since Lyra's 2026-07-23 quiet re-tune her mix is the quieter of the two — 46% cooldown, ≤3 likes/gap, and no drain-mode idle-likes at all; X's numbers below are unchanged.) Invariants: every pattern acts the **same or less** than the legacy 4–8 fill, every gap stays inside the **[1s, 120s]** envelope (cooldown is the quiet exception at 60–120s), and nothing ever fires faster — the pattern layer only slows the account down. Explicit `likesPerGap` knobs disable the draw. **Idle-liking honors quiet gaps**: the pattern layer reduces scheduled likes (cooldown 0, light 1–3), freeing like-budget headroom the idle-like engine would otherwise spend refilling the pauses — so `shouldIdleLike` now consults `inQuietDrainGap` (drain mode only) and stays out of a cooldown gap, while ambient browsing still scrolls so the gap stays alive.

## Lights-out auto-drain (ported from the LinkedIn actuator, PR #446)

With **Options → auto-drain** ticked (requires *Autonomous*; both default OFF), the 5-min autonomy alarm calls `maybeAutoDrain` whenever the daily auto-start declines: cheap pure gates first (`shouldAutoDrain` — window hours, STOP-day block, 30-min re-arm cooldown that fails closed on a skewed stamp), then the same fail-closed safety gate as the daily auto-start (`x-health` ok + post-challenge cooldown), then a real queue fetch and a re-check with the actual pending count. The `actuator.lastAutoDrainMs` stamp is written BEFORE `startDrain()` so a mid-start crash can't machine-gun restarts, and a manual STOP stamps `actuator.lastManualStopDay`, silencing both autonomy paths for the day. Consent is standing and server-side: the unattended path never arms `reply_send_enabled` — the `/api/actionable-x` gate honors `agent_instances.auto_send_enabled` (dashboard-set) as durable lights-out consent, and `pauseAllSending` clears both flags. Because `auto_send_enabled` on X ALSO arms the x-intern API-autosend pipeline, the approval pool is partitioned by `auto_send_target_at` (stamped ⇒ API autosend owns it, never served to the actuator) and the extension re-verifies every approval via `GET /api/actuator/approval-state/:id` immediately before posting (fail-closed `preSendDecision`) — see `docs/x-account-safety.md` §9. Same section covers the unattended pacing caution (`drainShortBandProb`).
**Stalled-run recovery (ported from the LinkedIn actuator).** `maybeAutoDrain` can't help a run that is `"running"` but wedged (its `runActive` gate skips). So the autonomy alarm also runs `maybeRecoverStalledRun`: when a run is provably stalled — drafts loaded, reply slots overdue, no post for `STALL_RECOVER_MIN` (20 min) past warm-up — it supersedes it with a fresh drain, behind the same safety gates and **sharing the 30-min re-arm stamp** (so a false positive starts at most one drain per window). Never arms sending; the pre-send `approval-state` revalidation still fail-closes each post. See `docs/linkedin-actuator.md` § *Stalled-run recovery* for the full invariant list.

**Self-reload on deploy (no chrome://extensions click).** `wxt build` embeds a build stamp in the bundle and writes the same stamp to `.output/chrome-mv3/build-stamp.json`. Token-authed `GET /api/actuator/x-extension-build` serves the on-disk stamp (fail-soft `null` when unreadable; path override `NOELLE_X_EXT_STAMP_PATH`). On the 5-minute alarm the extension compares stamps and calls `chrome.runtime.reload()` when a newer build landed, which re-reads the unpacked dir. Never during a run; one attempt per served stamp, so a machine whose unpacked copy is not synced to the served build (e.g. the laptop) tries once and stays quiet instead of looping. Works independently of the autonomy checkboxes, so every merge-driven deploy reaches the browser on its own.

## Full automatic (ported from the LinkedIn actuator)

> **Renamed 2026-07-26.** The panel now reads **Auto** (was "Full automatic"),
> **Manual Auto** (was "Drain all approvals"), and adds **Auto notifications**.
> The manual `Run` button and the Window/Comments/Likes inputs were removed —
> `startRun` still exists and is still used by the lights-out auto-start, it just
> has no manual surface. Commands (`startFullAuto` / `startDrain`) are unchanged,
> so everything below still applies under the new labels. The third button is
> documented in `docs/notifications-actor.md`.

A third panel button, **Full automatic** (`startFullAuto` → `startDrain({ manual: true, curfew: true })`), sits under *Drain all approvals*. It is the same persistent drain — post every approved reply, then stay alive watching the queue (`drainShouldKeepWaiting`, ~75 s polls) so replies approved later go out with no re-click — with one difference: it flags the run **unattended**, which turns on the overnight **posting-curfew** (`RunState.curfewEnabled` → `isWriteCurfew(atMs, enabled)`, local **1am–9am**, `src/lib/curfew.ts`). Only STOP, a challenge halt, or the runaway `MAX_DRAIN_ROUNDS` ceiling ends it.

**Why two drain buttons.** Both are the SAME durable, set-and-forget persistent drain (below) — they differ by **exactly one thing: the overnight curfew.** "Drain all approvals" is curfew-free — a 2am approval goes out at 2am. "Full automatic" adds the curfew for leave-it-running-overnight: nobody is watching, so it must not reply at 3am. Held slots are deferred (`deferLater`) and fire after 9am; the curfew is scoped to **posts** (`isPost` — replies, plus the inert `dm` kind), so likes and ambient browsing continue overnight and the session still looks alive. The same `{ curfew: true }` rides on every unattended start — daily auto-start, lights-out auto-drain, stall-recovery — regardless of which button was pressed; manual **Run** and **Drain** never curfew (`WRITE_CURFEW_ENABLED` stays the disabled global default). As everywhere on X, none of these paths arms `reply_send_enabled`: consent is still the standing switch on the Vega agent page.

**Durable across reload / restart / SW-death (`DRAIN_INTENT_KEY`) — BOTH buttons.** The live run lives in `chrome.storage.session`, which `chrome.runtime.reload()` **wipes** — so a self-update onto a new build would silently stop the drain and need a re-click (observed: a run died ~20 min after a rebuild bumped the served stamp, then 1h46m dead until a manual re-click). So **each drain button** persists a **standing intent** in `chrome.storage.local` — `DRAIN_INTENT_KEY` holds `{ curfew }` (Drain → `false`, Full automatic → `true`), set on the click and cleared **only by STOP** (a legacy bare `true` from an older Full-auto build is read as `{curfew:true}`). `checkDrainResume` — wired into both alarms and `onStartup`/`onInstalled` — restarts the drain within seconds of any death (self-reload, SW restart, browser relaunch, closed-then-reopened tab) **with the operator's curfew choice**, via the pure `shouldResumeDrain` (intent set ∧ no live run ∧ `passesAutoStartSafety`), so a freshly-challenged account still holds off and resumes only once clean — no re-click. This also makes the self-update genuinely invisible: `checkSelfReload` permits a reload of a *live-but-idle* drain (`runResumable`, guarded on empty pools so no in-flight reply is cut), because `checkDrainResume` immediately brings it back on the new build. STOP remains the one true off switch. (Reddit/Orion has only a Drain button and does not yet carry this durable intent.)

## Send integrity (2026-07: ported from the LinkedIn actuator, PRs #408/#410/#420)

The Lyra send-reliability fixes are ported to `apps/x-actuator`:

- **No double-posting (#408).** A reply is recorded done LOCALLY (doneDraftIds) *before* `markSent`, which is retried with backoff (`markSentWithRetry`, 4 attempts, epoch-aware); an unconfirmed markSent logs a `marksent-unconfirmed` skip for reconcile instead of re-serving — and re-posting — the draft. An in-session per-tweet guard (`RunState.actionedUrls`, keyed on the numeric status id via `lib/urn.ts`) drops a second queued draft for the same tweet as `duplicate-post`.
- **Reply-also-likes (#408) — opt-in, DEFAULT OFF.** After a successful reply the extension can also like the replied tweet (`locatePostLike`, best-effort, uncounted). Unlike LinkedIn (always-on), it ships behind the Options checkbox `replyAlsoLikes` because likes are a higher-risk uncapped write on X (see `docs/x-account-safety.md`).
- **Standalone likes land (#410).** Before a scheduled like the tab is pulled back to `x.com/home` (`ensureOnHome` / `lib/feed.ts` — scheduled-mode replies used to park it on the `/status/` permalink); the like skip reason is now self-diagnosing (`no-likeable-tweet(tweets=,withBtn=,btns=,path=)`); and `findFeedTweets` gains a drift-resistant fallback that derives tweet containers by climbing from their like/unlike buttons (shared `LIKE_BUTTON_SELECTORS`) when the `article[data-testid='tweet']` wrapper churns.
- **Verified submit (#420).** `doComment` delegates to `submitReply`: poll (~12s) for an ENABLED `tweetButton(Inline)`, click, then CONFIRM the composer cleared (`readCommentBox`; X clears/unmounts it on success) before reporting ok; fallback is a ⌘/Ctrl+Enter chord (`Cdp.pressSubmitChord`) with a posted re-check between chords so it can never double-post. Failures name the stage (`reply-failed:box-not-found|nav-or-type-error|submit-not-found|not-cleared|gesture-error`) and are never marked sent. The submit orchestration lives in `background/submit.ts` (`runSubmitReply`, pure + dependency-injected + tested) and NEVER throws: a mid-gesture CDP throw (e.g. the operator dismisses the chrome.debugger infobar, detaching the debugger after a click/chord already went out) is reported as `gesture-error` with the `dispatched` flag preserved instead of escaping to the generic tick catch (which would silently re-serve — and re-post — a maybe-posted draft). The retry policy (`replyFailureDecision`, pure + tested) is split on whether a submit gesture was dispatched: **pre-dispatch** failures (`box-not-found`, `nav-or-type-error`, a pre-gesture throw) re-queue at the BACK of the pool with a per-draft cap (`MAX_ACTION_TRIES`=3, then `gave-up-after-N` drops the draft for the session — one bad target can't starve the pool); **post-dispatch** failures (`not-cleared`, `submit-not-found` — its chord fallback fires either way — and a dispatched `gesture-error`) are AMBIGUOUS (the post may have landed slower than the observation window) and are dropped on the first failure (`ambiguous-dropped`, tweet stamped into `actionedUrls` so sibling drafts die as `duplicate-post`) — never retried, because retrying an ambiguous submit can re-post the same reply. A dropped draft is not markSent, and its skip row is stamped with the `tweet_id`, which the server dedup (next bullet) counts as reply evidence — so the still-pending approval is **not** re-served in a later session either (cross-session retry of a maybe-landed submit is the same duplicate-reply risk, just later). The operator reconciles the pending approval by hand (send manually or reject).
- **Persistent dedup-by-link (#420) — always on.** `GET /api/actionable-x` excludes any tweet already — or possibly already — replied to, keyed on the tweet id (`fetchXRepliedTweetIds`): 'sent' reply approvals (via `leads.external_id`, authoritative, no backfill) unioned with `x_activity` rows stamped with `tweet_id` at post time (independent of markSent — the approval-id stamp also makes the per-author daily cap join work). The stamped rows are both `type='reply'` (confirmed landings whose markSent may have failed) **and** `type='skip'` (the `ambiguous-dropped` rows: a submit was dispatched, landing never confirmed — fail closed, may-have-landed counts as landed, so the pending approval is never re-served). Those are the only skip rows carrying a `tweet_id`; the stamp is a deliberate permanent reply-block, so never stamp `tweet_id` onto other skip reasons. `'like'` rows also carry `tweet_id` and are excluded (liked ≠ replied). Fail-CLOSED: on a query error the route serves an empty 200 queue. Migration `0086_x_reply_dedup.sql` adds the partial lookup index (`type in ('reply','skip') and tweet_id is not null`).
